# V4c：如何验证 V4a 是否有收益

V4a 和 V4b 的正确性通过后，再做 V4c。V4a 与 V3 都是 GEMM，可以比较；V4b 只是复制实验，不能直接拿它的时间与 GEMM 比较，也不能声称 V4b 已优化 GEMM。

## 1. 假设与可证伪结果

假设：每线程连续复用一个 packed word，可能减少重复的读取或指令，从而改善某些形状的 kernel 时间。另一种可能是编译器已经消除了 V3 的重复操作，或者 V4a 带来的额外寄存器、循环/指令开销抵消收益。两种结果都要保留，不预设会变快。

```text
相同逻辑 Q/Z/S、BF16 A、相同 M/N/K 与 FP32 输出
        ├─ V3：每个 k 独立调用 decode
        └─ V4a：每个 word 分 8 次解码并累加
                     ↓
        都通过独立 CPU 参考、同一容差
                     ↓
        对照生成代码/资源 → 计时 → 有条件再用 profiler
```

## 2. 比较前先固定口径

- 相同 GPU、工具链、编译架构与优化参数，记录 GPU 型号/驱动/runtime、空闲情况、源码身份。
- 相同 A、逻辑 Q、P、Z、S、输出 dtype、布局、shape、合法范围与数值参考；两边都在正确性通过后计时。
- 使用 CUDA event 测已经准备好 GPU 输入后的**裸 kernel**；V3e checked 入口的 CPU 复制和同步不计入这一实验；不要把不同接口的计时边界混在一起。
- 先 warmup，分批重复多次，交替执行两个版本，记录各批均值、批均值 p50/p90、重复次数和原始数据；批均值分布不是单次延迟分布。包括小 M 与较大 M，先用 V3 固定例，再选择额外 shape。
- 同一机器检查 `-Xptxas=-v` 报告的寄存器、静态 shared 和 spill；用 `cuobjdump --dump-sass` 检查实际生成指令，源码循环结构不能直接当硬件访存次数。若 profiler 可用且权限允许，记录实际采集的指标与条件；没有权限就说明，不虚构数据。
- 至少计算 `V3 时间 / V4a 时间`；结果小于 1 就是该条件下 V4a 更慢。若波动与差距同量级，不声称稳定加速。

## 3. 本次实测：V3 与 V4a

2026-11-22 在 RTX 4090、驱动 535.309.01、CUDA 12.1（nvcc 12.1.66）、`sm_89 -O2 -lineinfo` 上测量，选用物理 GPU 1，UUID `GPU-deb35ff6-c14d-e1d9-5b24-8a7e4eb1bbd9`。运行前 `nvidia-smi` 显示该设备无进程、GPU 利用率 0%。GPU 时钟没有锁定；不能把该数据当作跨机器、跨时间的保证。

使用 [v4c_benchmark.cu](../benchmarks/v4c_benchmark.cu) 直接调用你完成的 V3/V4a；对应代码、二进制哈希和原始日志见 [v4c_results](v4c_results/)。为使基准能 include V4a，在 V4a 原测试 `main` 外增加了 `V4A_NO_MAIN` 宏保护，GPU kernel 的计算代码没有修改。输入使用同一份原始逻辑 Q/Z/S 与 BF16 A；CPU 从逻辑 Q 独立计算带 BF16 权重舍入的参考。对每个 case，两个版本均在测试先通过后才计时。阈值固定为 `atol=0.0001, rtol=0.00001`；本批数据的最大、平均绝对误差均为 0，不能推广为一般输入逐位相等。`memcheck --check` 对四个 case 报告 0 错误。

每个版本 warmup 20 次；每个形状交替测量 15 批，每批 100 次连续发射，用 CUDA event 的一批时间除以 100。表中的 p50/p90 是**每批平均耗时**的分位数，单位微秒；短 kernel 的批量计时仍可能受 host 发射供给、设备状态等影响，不是单次延迟分布。

| M | N | K | V3 p50 / p90 (µs) | V4a p50 / p90 (µs) | V3 p50 / V4a p50 |
|---:|---:|---:|---:|---:|---:|
| 1 | 128 | 256 | 8.151 / 8.161 | 6.770 / 6.780 | 1.204× |
| 16 | 128 | 256 | 9.708 / 9.718 | 7.762 / 7.772 | 1.251× |
| 128 | 128 | 256 | 9.708 / 9.718 | 7.772 / 7.791 | 1.249× |
| 128 | 512 | 1024 | 45.343 / 45.363 | 30.976 / 31.027 | 1.464× |

这四个合成输入、当前机器与计时口径下，V4a 的批均值 p50 均低于 V3。这里没有比较 Marlin，也没有把 V4b 的复制实验计入 GEMM。

## 4. 编译资源与能否解释原因

`ptxas` 和 `cuobjdump --dump-resource-usage` 显示：V3 每线程 26 个寄存器，V4a 为 36 个；两者均为 0 字节静态 shared、0 字节 stack、0 spill loads/stores。资源统计是该次编译的静态信息，不等于实际 occupancy 或性能瓶颈。

查看 [SASS 输出](v4c_results/sass.txt) 可见两者都生成了 `LDG` 全局读取；V4a 的代码中包含一次 32-bit word 读取及展开的 BF16 激活读取，但静态指令出现次数不是运行时执行次数，也不能据此推算 DRAM 请求或缓存命中。V4a 复用 word 的设计与计时改善一致，**尚不能证明它就是加速的唯一原因**，也不能说 DRAM 流量下降了多少。

尝试了 CUDA 12.1 自带 Nsight Compute 2023.1，对 `v4a_gemm` 采集周期和 DRAM 读取量；返回 `ERR_NVGPUCTRPERM`，本账号没有设备性能计数器权限，因此没有采到任何指标。系统 PATH 中的旧版 ncu 还因 section/rules 路径问题无法运行。没有修改驱动或权限；profiling 期间的计时受工具干扰，**不作为上表数据**。详细输出见 [ncu_12_1.log](v4c_results/ncu_12_1.log) 和 [ncu.log](v4c_results/ncu.log)。

## 5. 复现

```bash
/usr/local/cuda-12.1/bin/nvcc -arch=sm_89 -O2 -lineinfo -Xptxas=-v \
  benchmarks/v4c_benchmark.cu -o /tmp/quant_v4c_benchmark
nvidia-smi
CUDA_VISIBLE_DEVICES=1 /tmp/quant_v4c_benchmark
CUDA_VISIBLE_DEVICES=1 /usr/local/cuda-12.1/bin/compute-sanitizer \
  --tool memcheck --error-exitcode 1 /tmp/quant_v4c_benchmark --check
```

先确认 GPU 空闲；GPU 1 是本次所用设备。`--check` 只做正确性，不执行计时，适合 sanitizer。输出、各批原始数据、编译资源和 SASS 的命令结果见 `v4c_results/`；`ncu_12_1.log` 的权限错误是现有环境限制，而不是性能数据。
