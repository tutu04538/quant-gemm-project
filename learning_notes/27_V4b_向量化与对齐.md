# V4b：先独立理解 16 字节向量访问

## 1. 目标和范围

V4a 复用同一列沿 K 打包的一个 word。现在考虑另一个方向：P 的每一行按 N 连续排列，相邻四个列对应四个连续 uint32，可以尝试一次 16 字节访问。本节先用独立复制实验搞懂对齐与边界；**它不是 GEMM，也尚未整合进 V4a，不能用它声称 GEMM 已经向量化或加速**。

数据：`src` 和 `dst` 是同样形状的行优先 uint32 矩阵 `[rows,N]`，每个 word 可看作一个 packed Q，但复制实验不解码它。输入输出由不同 `cudaMalloc` 分配，不重叠；N、rows 为正。测试通过偏移指针产生 4 字节对齐但不一定 16 字节对齐的地址；行之间没有 padding。

## 2. 画出线程与内存

每个 block 32 条线程，每个线程处理同一行的最多 4 列：

```text
row=0、N=9：
物理 src：[w0][w1][w2][w3] [w4][w5][w6][w7] [w8]
           └──── lane 0 ───┘ └──── lane 1 ───┘ └lane 2┘
                  4 words            4 words       1 word
物理 dst：对应相同位置；每条线程只写自己的区域

lane 0：有 4 个元素，首地址对齐时可读写一个 uint4
lane 1：同上
lane 2：只剩 1 个元素，必须走标量尾部
lane 3..31：列起点越界，直接 return
```

`blockIdx.y` 选择行；x 方向每个线程的起始列相差 4。N 大于 128 时，一个 row 由多个 block 分段，线程区域仍然互不重叠。该 copy kernel 的一个 warp 共覆盖最多 128 个 word；它与 V4a 的 GEMM warp 输出分工不同。

## 3. 为什么指针和行步长都影响对齐

`uint4` 可看作 4 个 uint32（16 字节）。CUDA 的 `uint4` 访问需要 16 字节对齐的起始地址；既要检查读取地址，也要检查写入地址，还要保证这一行剩余 4 个元素都有效。每个元素本身只有 4 字节：

```text
假设 src 基地址 16 字节对齐，N=5：
row 0 首址 = base +  0 bytes → 对齐
row 1 首址 = base + 20 bytes → 余 4，不是 16 字节对齐
row 2 首址 = base + 40 bytes → 余 8，不是 16 字节对齐
```

即使第 0 行对齐，也不能假定每一行都对齐。若源地址或目的地址偏移一个 uint32，就增加 4 字节；即使 N=16，每行的起点也仍然不是 16 字节对齐。对于不满足条件的组，逐个复制有效元素即可，**不可先做未对齐的 uint4 加载再打算丢弃越界元素**。

例如 N=9，row 0 的 col=4，若 src 和 dst 首址都 16 字节对齐，则指向该组的地址各增加 `4*4=16` 字节，仍对齐，且 col 4～7 均有效。col=8 只剩一个元素，即使地址碰巧对齐也不能读取 4 个。

## 4. C++ 语法和练习

`src + index` 对 `uint32_t*` 是按 **uint32 元素**偏移；如果 index=4，地址增加 16 字节。`reinterpret_cast<const uint4*>(sp)` 把地址解释为指向 4 个 uint32 的向量指针，它**不修改原地址，也不会自动检查对齐或容量**。`reinterpret_cast<uintptr_t>(sp) % 16` 可在此环境中检查地址的 16 字节对齐。读取和写入分别通过 `const uint4*` 和 `uint4*`。

复制 [v4b_vector_load_template.cu](../kernels/marlin_from_scratch/v4b_vector_load_template.cu) 为 `v4b_vector_load.cu`，填三个 TODO：

1. 计算每个线程的 src/dst 组首指针；行步长是 N 个 uint32。
2. 只有当前行中 4 个元素全部有效、源和目的组首地址都满足 16 字节对齐时，做一个 uint4 读和一个 uint4 写。
3. 其他情况逐个复制本组中 `col+i<N` 的元素。

```bash
cp kernels/marlin_from_scratch/v4b_vector_load_template.cu kernels/marlin_from_scratch/v4b_vector_load.cu
/usr/local/cuda-12.1/bin/nvcc -arch=sm_89 -O2 -lineinfo \
  kernels/marlin_from_scratch/v4b_vector_load.cu -o /tmp/quant_v4b
nvidia-smi
CUDA_VISIBLE_DEVICES=1 /tmp/quant_v4b
```

测试覆盖 N=1、3、4、5、9、16、17、129，3 行，源或目的分别偏移 0/1 个 word，并用 guard 检测越界写。临时参考填充在 CUDA 12.1、RTX 4090、SM89 上各例通过，memcheck 0 错误；你的实现尚需独立检查。测试结果正确不证明实际执行了向量指令：review 时还要检查代码和生成的指令。

你的实现验证：2026-11-22，CUDA 12.1、`sm_89`、`-O2 -lineinfo`，RTX 4090 上所有模板测试通过，`memcheck` 为 0 错误。检查代码可知各线程只写自己负责的最多 4 个 word；`cuobjdump --dump-sass` 中看到 `LDG.E.128` 和 `STG.E.128`，说明编译产物包含 128-bit 读写指令，但这本身不证明某次运行的执行次数或性能收益。

这个实验只验证复制模式；要把向量读用于 GEMM，需要重新设计每个线程/warp 拿到的列，并保证数据与计算的所有权匹配，我们目前没有完成该集成。
