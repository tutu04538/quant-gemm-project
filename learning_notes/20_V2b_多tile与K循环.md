# V2b：多个 WMMA 输出 tile 和 K 循环

本节在 V2a 正确后开始。目标仍是 BF16 A/B、FP32 accumulator 和输出；使用多个 block，每个 block 的一个 warp 负责一个 `16×16` 输出 tile。

## 1. 当前契约

本版只接受正的、均能被 16 整除的 M/N/K；A/B/C 分别为行连续的 `[M,K]`、`[K,N]`、`[M,N]`，设备分配独立。它**不处理非整除尾部，也不自动 padding**；共用 host 检查会拒绝不符合形状约定的 case。指针和步长由模板控制，不是通用张量 API。

## 2. 固定例子的 block、warp 与数据流

对 `M=16,N=128,K=256`：

```text
C [16,128] 分成 8 个 16×16 输出 tile
      ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
行 0～15 │block0│block1│block2│block3│block4│block5│block6│block7│
      └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘

每 block：一个 warp、32 条 lane；在本 block 的输出 tile 上执行 16 次 K 轮：

A 的 tile [16,16] ─┐
                    ├→ WMMA fragment → FP32 accumulator 累加
B 的 tile [16,16] ─┘        （base=0,16,...,240）
                                             ↓
                               最后一轮之后写一次 C tile
```

例如 block `(1,0)` 负责行 0～15、列 16～31。`base=0` 时它读 A[0:16,0:16] 和 B[0:16,16:32]；`base=16` 时读 A[0:16,16:32] 和 B[16:32,16:32]。相邻 block 可以读到同一 A tile；此处先做正确版本，不假设缓存或复用性能。

## 3. 一个输出如何跨轮累加

设每个 K 项对 C[0,16] 的乘积都是 1。第一轮 K=0～15 的贡献是 16；第二轮 K=16～31 再加 16，accumulator 为 32。完整 K=256 时共 16 轮，结果是 256。若每轮都把 accumulator 清零，最后只留下最后一轮，这是要特别避免的错误。

## 4. 动手

复制 [v2b_wmma_template.cu](../kernels/marlin_from_scratch/v2b_wmma_template.cu) 为同目录 `v2b_wmma.cu`。模板已经计算本 block 的输出左上角 `row,col` 并声明 fragment。完成清零、K 循环内加载 A/B tile、MMA 以及循环后写回。行优先地址：A 起点由 `row` 与 `base` 定位，B 起点由 `base` 与 `col` 定位，C 起点由 `row` 与 `col` 定位；各自 `ldm` 是整张矩阵的行步长，而不是 tile 宽度。

整个 warp 执行相同的 WMMA 调用；不能像 V0 那样给 lane 分别做边界返回。此版由 host 保证形状对齐，边界 tile 的 shared staging 留到后续。

## 5. 行步长和加载范围是两件事

对于行优先矩阵，行步长 `ldm` 是**相邻两行的起始地址相隔多少个元素**。本练习的矩阵紧密连续，因此它恰好等于整张矩阵的列数；如果将来允许行末有间隔或带 stride 的 view，这两个数未必相同。

加载范围由 `fragment` 的角色和模板形状确定。本例声明的 `matrix_a, 16,16,16` 是一个逻辑 `[16,16]` 的 A 片段，`matrix_b` 也是 `[16,16]` 的 B 片段。`load_matrix_sync` 的指针指定这个片段的左上角，`ldm` 告诉它怎样找到下一行。两者结合，并不意味着从每一行固定取整张矩阵的前 16 个元素。

例如 B 的逻辑形状 `[256,128]`，计算 `blockIdx.x=1`、`base=32` 时：

```text
B 的每行共 128 个 BF16 元素，行步长 ldm = 128

                  列 0～15   列 16～31              列 127
             ┌───────────┬───────────────┬───────┐
第 32 行     │           │  本次加载 16 个 │  ...  │
第 33 行     │           │  本次加载 16 个 │  ...  │
...          │           │      ...        │       │
第 47 行     │           │  本次加载 16 个 │  ...  │
             └───────────┴───────────────┴───────┘

左上角 B[32,16] 的线性元素索引 = 32*128+16 = 4112
下一行 B[33,16] 的线性元素索引 = 33*128+16 = 4240
```

两行左上角相差 128 个元素，但每行片段只涉及从列 16 开始的 16 个逻辑元素，整个片段涉及 16 行。`ldm` 不等于本次每行要加载的片段宽度。这里描述逻辑片段；32 条 lane 怎样协作、硬件实际如何组织访存，不能只凭这一张图判断。当前 V2b 只支持对齐且尺寸为 16 倍数的形状，指针与步长也需满足 WMMA 要求。

编译命令与 V2a 类似，将源文件和输出名替换为 `v2b_wmma.cu` 和 `/tmp/quant_v2b`；运行前确认 GPU 空闲。共用测试包含 `(M,N,K)=(16,16,16)、(16,32,32)、(32,16,48)、(16,128,256)`，每个 shape 有整数与 BF16 小数 case。完成后会做结果、内存检查和指令证据核对。
