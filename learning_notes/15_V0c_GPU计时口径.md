# V0c：为 V0 登记 GPU 计时口径

本节没有新的 kernel TODO。先完成并通过 V0b 的正确性检查，再使用同一个 V0 文件中的计时框架；此文档定义一次实验测什么、怎样解释输出。现在没有 V0 的正式性能结论。

## 1. 目标和测量边界

固定待测输入为 FP32、行连续、`M=128,N=192,K=256`，`block=(16,16)`；grid 使用向上取整计算，即 `(12,8)`。总共 96 个 block，每 block 256 个线程、8 个 warp、每 warp 32 lane，每个有效线程算一个 C 元素。

```text
计时前：CPU 生成 A/B → GPU 分配/复制 → 同形状正确性检查 → warmup 10 次

同一默认 stream：start event → 连续发射 100 次 V0 kernel → stop event
CPU：等待 stop → 取两个 event 的间隔 → 除以 100 得到这一批的平均毫秒数

重复 15 批 → 对 15 个“每批平均值”排序 → 报 p50、p90
```

计时区间包含这 100 次 kernel 在 stream 上的时间区间，可能受 GPU 调度及主机提交供给等因素影响；它**不包含**显存分配、输入复制、正确性检查和 warmup。它不是端到端时间，也不是 100 次单次延迟各自的分布。结果复制与释放在计时后。

## 2. 手算读懂结果

假设一批 100 次总计 `0.5 ms`，这一批的均值是 `0.5/100=0.005 ms/次`，即 `5 µs/次`。这是算术示例，不是当前设备的测量值。

模板收集 15 批、每批一个平均值；p50 取排序后第 8 个，p90 按最近秩法取第 `ceil(0.9*15)=14` 个（以 1 为起始计数）。因此输出的 p50/p90 是**批均值的分位数**，不等同于单次 kernel 延迟的 p50/p90。模板同时输出全部 15 个排序后的批均值，供记录和判断波动。

## 3. 如何运行与记录

在 V0b 的五个正确性 case 全部通过后：

```bash
nvidia-smi
CUDA_VISIBLE_DEVICES=1 /tmp/quant_gemm_v0 --bench
```

GPU 1 仅为示例；每次运行前确认对应卡空闲。模板会先重新跑 V0b 正确性，再独立验证 `128×256` 乘 `256×192`；只有该形状也通过才会计时。输出的 `driver API` 和 `runtime` 是 CUDA API 数值版本，不替代 `nvidia-smi` 的实际驱动版本，也不是编译器版本。

记录时至少保存：时间、GPU 型号及 UUID、驱动、nvcc 版本、源码版本/hash、完整编译命令、形状、dtype、布局、block/grid、输入生成方式、正确性标准和结果、GPU 其他占用、warmup、批次、每批重复数、所有样本和计时边界。必要时保存原始终端日志。只在同样的输入与边界下比较 V0/V1；不同设备、软件、时钟或后台任务可能影响结果。

参考框架用 `cudaEventRecord(start)` 标记起点、记录 stop、等待 stop 完成，最后用 `cudaEventElapsedTime` 获取毫秒数。等待 stop 保证同一 stream 中先前的工作已到达该标记；不代表其他 stream 的所有工作也都结束。

## 4. 正确性与工具

当前计时输入同样是小整数 FP32，因此模板可在已列形状内与 CPU 参考精确比较。今后更换随机浮点或 BF16 输入时，必须在测试前另定适当容差，记录最大/平均误差和超差数量；不能默认精确相等。

边界和性能分开验证。完成 V0b 后，助手会根据当时环境检查 CUDA 工具及 GPU 占用，必要时运行可用的 `compute-sanitizer`；硬件计数器权限或 profiler 支持不能事先假定。V0 是朴素正确性和计时起点，不以一次结果判断是否优化成功。
