# V1c：V0 与 V1 的正确性和性能对照

本节不新增 kernel 或模板。先完成 V1a/V1b，并通过正确性和必要的同步检查，再用 V0 与 V1 各自已有的计时框架做同条件对照。

## 1. 比较的两个计算方式

```text
V0：一个线程直接从 global memory 读取自己计算所需的 A/B 值

V1：一个 block 的 8 个 warp、256 个线程合作加载 A/B tile
    → block 内同步 → 每个线程复用 shared tile 累加
    → 读完同步 → 处理下一轮 → 写各自的 C
```

这里的 8 warp 来自两版相同的 `(16,16)` block；lane 由 `threadIdx.y*16+threadIdx.x` 确定。V1 的逻辑复用减少了什么重复读取可以从代码推导，但真实 global 流量还受到缓存等影响，必须测量才能判断。**不能只凭 shared memory 就断言更快或自动合并访问。**

## 2. 对照契约

两份模板的 `--bench` 都使用：

- 形状：A `[128,256]`、B `[256,192]`、C `[128,192]`，即 `M=128,N=192,K=256`。
- 类型与布局：FP32、行优先连续；相同的确定性小整数输入生成规则。
- launch：`block=(16,16)`、`grid=(12,8)`，同一 GPU、同一编译参数、同一默认 stream。
- 时间：warmup 10 次；15 批，每批 100 次发射，CUDA event 记录每批平均 GPU 时间，再对 15 个批均值报告 p50/p90 和全部样本。
- 计时范围：只包含 event 之间的 GPU stream 时间区间，可能受调度或主机提交供给影响；不包含显存分配、复制、正确性检查与 warmup。

两个模板先检查各自正确性，并在 benchmark 形状上再检查一次；只有通过才输出计时结果。本测试使用小整数且部分和可精确表示，不把其严格相等标准扩展到一般浮点输入。

## 3. 怎样测和记录

V0/V1 都使用同一编译器、架构和优化选项，例如本机的 CUDA 12.1：

```bash
/usr/local/cuda-12.1/bin/nvcc -arch=sm_89 -O2 -lineinfo \
    kernels/marlin_from_scratch/v0_gemm_template.cu -o /tmp/quant_gemm_v0
/usr/local/cuda-12.1/bin/nvcc -arch=sm_89 -O2 -lineinfo \
    kernels/marlin_from_scratch/v1_gemm.cu -o /tmp/quant_gemm_v1
nvidia-smi
CUDA_VISIBLE_DEVICES=1 /tmp/quant_gemm_v0 --bench
CUDA_VISIBLE_DEVICES=1 /tmp/quant_gemm_v1 --bench
```

以上 V0 文件名是本次用户填写的位置；如果你将 V0 另存，使用实际路径。V1 文件名同理。GPU 1 仅为示例，选择当时空闲的设备；测量前后记下占用，必要时交错重复两版以判断波动，不抢占其他任务。

记录时间、GPU 型号/UUID、驱动和 nvcc、两个源码的 hash、编译命令、输入、正确性结果、全部样本和 p50/p90。计时结果是**每批 100 次的均值**的分位数，不是单次延迟分布。若需表述比值，按相同 case 的 `V0 时间 / V1 时间` 计算，V1 更慢时如实报告小于 1；不要把某个 case 的结果推广到所有矩阵。

## 4. 提出可证伪的假设

示例假设：“V1 的 block 内复用让这个 shape 的重复 global 读取下降，收益超过同步和 shared 搬运开销。”需要用同条件正确性、GPU 时间和可用的 profiler 证据来检查。若观察到的时间没有改善，可能还需要分析访问、同步、缓存、寄存器和形状；仅凭猜测不能认定原因。profiler 或计数器不可用时记录具体限制，不编造指标。
